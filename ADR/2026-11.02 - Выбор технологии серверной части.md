**ADR: 2026-11.02 - Выбор технологии серверной части**

**Дата:** 18 ноября 2026 г.

**Статус:** Принято

**Контекст:**

На сервере нужны формы составов и матчей, вход пользователей, проверка прав, расчёты и подготовка материалов. Основная работа связана с обычными веб-страницами и данными, а не с отдельным публичным API.

**Ограничения:**

- Основной язык — Python; разработчику знаком SQL (LIM01).
- Один разработчик должен реализовать и интерфейс, и бизнес-логику (LIM02).
- Сохранение действия должно укладываться в одну секунду; тяжёлая обработка видео выносится из веб-запроса (PER01, PER06).

**Рассмотренные варианты:**

1. **Django:** готовые формы, шаблоны, ORM, миграции, пользователи и сеансы.
2. **FastAPI:** удобен для API, но для проекта потребуются дополнительные решения для форм, ORM, миграций и административного интерфейса.
3. **Flask:** небольшое ядро; больше частей приложения придётся подбирать и связывать самостоятельно.

**Решение:**

Использовать Python 3.13, Django 5.2 LTS и Psycopg 3 для работы с PostgreSQL. Устанавливать актуальные исправления этих веток; точные версии фиксировать в зависимостях при начале разработки.

**Обоснование:**

- Django закрывает большую часть типовых задач проекта без набора отдельных расширений.
- Python подходит для расчётов показателей и обработки данных.
- Поддержка Django 5.2 LTS до апреля 2028 года покрывает следующий учебный семестр.

**Недостатки решения:**

- Нужно изучить правила ORM, миграций и обработки запросов Django.
- Фреймворк не реализует спортивные правила, права на конкретный матч и защиту от повторных команд.
- Тяжёлый расчёт внутри веб-запроса всё равно ухудшит время ответа.

**Последствия:**

- Бизнес-правила размещаются в функциях модулей, а обработчики запросов принимают данные и возвращают ответ.
- Админка используется для справочников и служебных задач; изменение счёта в обход правил запрещается.
- Для первого релиза дополнительно нужны Matplotlib для инфографики и FFmpeg для видео. Они подключаются при реализации этих функций.
