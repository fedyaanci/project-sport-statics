**ADR: 2026-11.04 - Выбор системы хранения данных**

**Дата:** 18 ноября 2026 г.

**Статус:** Принято

**Контекст:**

Турниры, сезоны, команды, игроки, составы и действия связаны между собой. Нужно рассчитывать показатели по периодам, сохранять версии протоколов и применять импорт без повторных записей.

**Ограничения:**

- База данных — PostgreSQL, один экземпляр для приложения (LIM01, LIM02).
- Два оператора могут одновременно менять один матч (SCA02, DUR09).
- История игрока сохраняется при смене команды; внешний импорт не создаёт дубликаты (PRN08, DUR10).

**Рассмотренные варианты:**

1. **PostgreSQL:** связи, транзакции, ограничения целостности и SQL-агрегации.
2. **SQLite:** проще установить, но конкурентная запись и блокировки отличаются от рабочей PostgreSQL; не подходит под заданное ограничение.
3. **MongoDB:** подходит для документов, но основные данные проекта связаны, а выбор нарушает LIM01.

**Решение:**

Использовать PostgreSQL 18. Доступ из приложения — через ORM Django и Psycopg 3. Видео и готовые файлы хранить отдельно по ADR 09; в БД оставлять их параметры, состояние и путь.

**Обоснование:**

- Внешние ключи помогают не допустить действие для несуществующего матча или игрока.
- Уникальные ограничения защищают назначения, внешние идентификаторы и ключи повторных команд.
- SQL подходит для фильтров, группировки показателей и сравнения сезонов.

**Недостатки решения:**

- Для разработки и тестирования нужен отдельный сервер PostgreSQL.
- Индексы и ORM-запросы нужно проверять: наличие БД само по себе не обеспечивает время ответа.
- Один экземпляр БД остаётся общей точкой отказа.

**Последствия:**

- Игрок имеет постоянный идентификатор, а участие в команде и сезоне хранится отдельно.
- Для импортированных объектов задаётся уникальная связка источника, типа объекта и внешнего идентификатора.
- Изменения схемы выполняются миграциями; основные запросы индексируются по матчам, сезонам, игрокам и времени.
- Разработка и проверки конкурентной записи выполняются на PostgreSQL, а не на SQLite.
