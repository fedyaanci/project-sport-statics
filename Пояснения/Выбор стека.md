# Выбор стека

## Основной вариант

Для проекта выбраны **Python, Django и PostgreSQL**. Интерфейс будет на HTML-шаблонах Django с CSS. Для обновления табло понадобится небольшой JavaScript.

| Инструмент | Для чего нужен |
|---|---|
| Python 3.13 | Логика приложения и расчёты |
| Django 5.2 LTS | Веб-страницы, формы, пользователи, сеансы, ORM и миграции |
| PostgreSQL 18 | Хранение участников, матчей, действий и версий результатов |
| Psycopg 3 | Подключение Django к PostgreSQL |
| HTML, CSS, JavaScript | Пользовательские страницы и обновление табло |

Используются последние исправления выбранных версий. Перед началом разработки версии зависимостей нужно зафиксировать в проекте.

## Почему Django

В приложении много форм и связанных данных: команды, игроки, сезоны, матчи и составы. Также нужны вход, сеансы, права и работа администратора. Django уже даёт основу для этих задач. Поэтому не придётся отдельно подбирать ORM, миграции и несколько библиотек для обычного веб-приложения.

FastAPI тоже подходит для Python, особенно если главная задача — API. Но в этом проекте нужны ещё страницы, формы и административные операции. Flask даёт небольшое ядро, но больше дополнительных частей придётся собирать самостоятельно. Поэтому для учебного проекта я выбрал Django.

Готовый фреймворк не заменяет правила проекта. Проверку права оператора на конкретный матч, подтверждение почты и защиту от повторного действия нужно написать отдельно. Админка подходит для справочников, но не должна позволять менять счёт в обход правил и истории.

## Почему PostgreSQL

Здесь много связей, которые удобно хранить в SQL: игрок относится к заявке, состав — к матчу, действие — к игроку и матчу. Также нужны транзакции, уникальные ключи и проверки одновременных изменений.

SQLite проще установить, и его можно использовать для первого знакомства с Django. Но в пилоте уже предусмотрены два оператора и совместная запись. Поэтому разработку и проверку лучше вести на PostgreSQL, который останется в рабочей версии.

ORM Django не отменяет знание SQL. Оно понадобится для связей, индексов, группировки показателей и проверки сложных запросов. Вторая ORM для этого проекта не нужна.

## Почему обычные шаблоны

Большая часть экранов — формы, таблицы и страницы результатов. Их можно сделать средствами Django. Отдельный frontend с собственной сборкой увеличил бы объём работы.

Табло может получать небольшой ответ с показателями через `fetch` примерно раз в секунду. Сначала нужно проверить, укладывается ли такой способ в требования по задержке и нагрузке. Если этого окажется мало, способ обновления можно будет изменить.

## Что понадобится позже

| Функция | Решение |
|---|---|
| Показатели и сравнения | SQL-агрегации и обычный Python |
| Отчёт | Сохранённый HTML-файл. Его можно распечатать в PDF средствами браузера |
| Инфографика и графики | Matplotlib в первом релизе |
| Обработка видео | FFmpeg в первом релизе |
| Длительные задания | Служебная команда того же проекта с сохранением попыток и статусов в БД |
| Прогноз | Согласованный расчёт на Python и SQL; готовая большая ML-платформа заранее не нужна |

Файлы видео и материалов хранятся отдельно от строк БД. В базе остаются ссылки, параметры и состояния. Доступ к файлам проверяется приложением. Для восстановления нужны копии и базы, и файлов.

В MVP достаточно одного приложения и одной базы. Отдельные серверы кэша, брокер сообщений и микросервисы пока не обоснованы нагрузкой. Если позже появится конкретная проблема, её решение можно будет добавить отдельно.

Для разработки достаточно IDE, `venv`, `pip` и PostgreSQL. Сервер приложения и HTTPS для сетевого запуска выбираются на этапе развёртывания. Встроенный сервер Django используется только для локальной разработки.

## Почему выбранные версии подходят

Django 5.2 LTS поддерживается до апреля 2028 года и совместим с Python 3.13. PostgreSQL 18 поддерживается до ноября 2030 года и подходит для Django 5.2. Эти сроки покрывают следующий учебный семестр. Проверка выполнена по официальной документации.
