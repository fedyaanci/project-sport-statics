**ADR: 2026-11.03 - Выбор технологии интерфейса**

**Дата:** 18 ноября 2026 г.

**Статус:** Принято

**Контекст:**

Пользователи заполняют формы, работают со списками и смотрят статистику. Постоянное обновление без перезагрузки требуется прежде всего онлайн-табло и состоянию обработки материалов.

**Ограничения:**

- Одно веб-приложение разрабатывает один человек (LIM02).
- Работа идёт через браузер с подключением к сети (LIM04).
- Нужны актуальные Chrome, Firefox, Edge и интерфейс от 360 пикселей в ширину, включая Chrome на Android (PLT01, PLT02).

**Рассмотренные варианты:**

1. **Шаблоны Django, CSS и JavaScript:** страницы формируются сервером, отдельные блоки обновляются запросами из браузера.
2. **React или Vue:** отдельное клиентское приложение; дополнительно нужны сборка, API и согласование состояния клиента с сервером.
3. **Только Django Admin:** быстро для справочников, но неудобно для зрителя, оператора матча и просмотра статистики.

**Решение:**

Создавать пользовательские страницы на шаблонах Django с адаптивным CSS. Использовать обычный JavaScript и `fetch` для табло и статусов заданий. Небольшие ответы JSON формировать средствами Django без отдельного API-фреймворка.

**Обоснование:**

- Для форм и таблиц не требуется отдельное клиентское приложение.
- Один проект содержит страницы, проверку форм и бизнес-правила.
- Можно постепенно добавлять обновление отдельных частей страницы.

**Недостатки решения:**

- Часть переходов и отправок форм будет перезагружать страницу.
- При усложнении интерфейса обычный JavaScript потребует аккуратной организации.
- Взаимодействие без сети не поддерживается.

**Последствия:**

- Все важные проверки выполняются сервером, даже если уже выполнены в браузере.
- Формы изменения данных используют CSRF-защиту. Доступность кнопки не считается проверкой прав.
- Мобильная ширина и обновление табло проверяются в настоящем браузере; серверных тестов для этого недостаточно.
